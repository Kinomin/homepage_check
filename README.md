# School Insight AI — 実装キックオフ資料

このフォルダには、私立中高一貫校向けホームページ分析ツールの実装に必要な資料一式が入っている。

## 読む順番

1. この README で全体像と絶対制約を把握する
2. `prototype.html` をブラウザで開き、01〜07の全画面を実際に操作する。特に **02 欠落マップ**（セルをクリックして根拠パネルを見る）と **06 改善アクション**（グループ化切り替え・照会欄）は操作しないと構造が分からない
3. `handoff.md` を通読する。データモデル（3章）と判定ルール（4章）が実装の核
4. `handoff.md` 10章（QA記録）に目を通す。プロトタイプで実際に起きたバグと、実装で再発させないための設計上の含意をまとめてある

## この製品が何であるか

私立中高一貫校の入試広報担当者が、自校サイトと比較校サイトを客観的に比べ、何をすべきかを事実ベースで把握するための分析ツール。**学校を採点するツールではない。**「情報が公開されているか」という事実の記録に徹し、優劣の評価や煽り文句は生成しない。

3つの計測画面が、それぞれ別の問いに答える：

- **02 欠落マップ** — すでにサイトに来た人が、探した情報を見つけられるか
- **03 導線の実測** — 来た人が説明会の申込にたどり着けるか
- **04 発見のされ方** — そもそも、まだ学校名を知らない人に届いているか

05（ペルソナ仮説）と06（改善アクション）はこの3つを解釈する層。01（サマリー）と07（レポート出力）は提示する層。

## 絶対に外してはいけない5つの制約

実装のどこかで判断に迷ったとき、この5つに立ち返ること。

1. **計測と解釈を分離する。** 02・03・04で表示される数値・事実は機械判定のみで、LLMの解釈を混ぜない。LLMの解釈が入るのは05・06だけで、そこには必ず根拠（criterion_idやURL）を紐付ける。
2. **語句一致で判定しない。** 「探究学習」は学校によって「自調自考論文」「BEYOND」等、名称が全く異なる。ページ内容から意味で判定するパイプラインが必須（詳細は `handoff.md` 4章）。
3. **比較校を採点しない。** 公開の有無・更新日・件数という事実のみを記録する。評価文・優劣の断定は比較校に対して生成しない。
4. **走査失敗と「情報がない」を区別する。** robots.txt拒否・タイムアウト等で取得できなかった場合は `unknown`。これを `none`(欠落)と同じ扱いにすると、取得失敗が「他校にあってお宅にない」という誤った指摘に化ける。
5. **所要時間・期限を生成しない。** 改善アクションに時間見積もりや期限を付けない。学校ごとに体制が違いすぎ、こちらが決めてよい数字ではない。優先度と難易度（「校内でどこまで話を通す必要があるか」）で示す。

まず作るのは 02 欠落マップ／03 導線の実測／06 改善アクション／07 レポート出力／01 サマリー。
04（発見のされ方）と05（ペルソナ仮説）は Phase 2。理由は `handoff.md` 8章・9章Dを参照（順位計測APIの課金設計が前提のため）。

## 実装前に人間の判断が必要な事項（`handoff.md` 9章）

以下はコードを書き始める前に、発注者側と合意しておくべき事項。仕様として決め切れていない。

- 比較校を全ページ走査するか、判定に必要なページのみに絞るか
- LLM判定のコスト（週次800判定規模）をどう抑えるか、自校と比較校で頻度を変えるか
- LLM判定の揺れ（同じ入力でも結果が変わりうる）をどう扱うか

## デザインの引き継ぎ

`prototype.html` の余白・罫線の太さ・数値の等幅表記をデザインシステムの基準にしている。
見出しは Shippori Mincho、本文は Zen Kaku Gothic New、数値は IBM Plex Mono。

配色は実装時に**紙の色（象牙・生成り）へ寄せた**。学校に出す資料として読まれるものなので、
青灰のダッシュボードらしさより、書類としての落ち着きを取っている。彩度は上げず、
グラデーション・強い影・原色は使わない。

**文字色はすべて、載る背景に対して 4.5:1 以上**（WCAG AA・通常サイズ）を確保している。
9.5〜11px の小さいラベルが多いため、大きい字向けの 3:1 では足りない。
配色を変えたら `npm run check:contrast` で検算すること（CI でも通している）。

## 起動

```bash
npm install
npm run dev                  # http://localhost:3000
```

設定なしで全画面が動く。その場合は `prototype.html` 由来のサンプルデータが表示され、
画面上部に「サンプルデータを表示しています」と明示される。

## 公開URL

**設定が済めば、以降はURLを開くだけ。** ローカルで何かを起動する必要はない。
構成は3つに分かれる。

| 何を | どこで | なぜそこか |
|---|---|---|
| 画面（URL） | Vercel | 常時稼働。push すれば自動でデプロイされる |
| データ | Supabase | Postgres と認証。RLS で組織を分離する |
| 走査（定期実行） | GitHub Actions | サーバレスの実行時間上限を避けるため |

- **デプロイのたびにマイグレーションが自動で当たる**（`vercel.json` の Build Command が
  `scripts/vercel-build.ts` を指している）。Production デプロイのときだけ流し、
  プレビュー環境のビルドは本番のデータベースに触らない
- **走査は `.github/workflows/scan.yml`** が週1回（月曜 6:00 JST）に起動する。
  設定画面の既定（自校 週次・月曜・6時）に合わせてある。Vercel の関数で回さないのは、
  31項目 × 校数のLLM判定とクロールが関数の実行時間上限（Pro でも 800 秒）を超えるため
- **失敗した学校は水曜・金曜に拾い直す。** 走査の間隔は週1回のまま。
  前回走査として数えるのは走り切った回だけなので（`status='done'` で絞っている）、
  失敗した学校は次に起きたときも対象に残り、成功した学校は次の月曜まで対象にならない。
  全部成功していれば拾い直しの回は0校で終わる
- **作業中のブランチにもURLが出る。** Vercel はブランチごとにプレビューURLを作るので、
  開発でもローカルを立ち上げる必要はない（`docs/SETUP.md` の「開発用のURL」）
- **`.github/workflows/keepalive.yml`** が3日ごとにデータベースを読む。
  Supabase の無料プランは7日間アクセスが無いと一時停止し、走査の週1回では
  間隔が並ぶため。有料プランなら不要

手順は **[docs/SETUP.md](docs/SETUP.md)** の 7. にまとめてある。1回で終わる。

## Supabase の初期化

```bash
npm run db:migrate
```

`supabase/migrations/` を番号順に適用し、調査項目31件のシードを流す。適用済みは
`schema_migrations` に記録するので、再実行しても二重には流れない。1ファイル=1トランザクションで、
途中で失敗したファイルは丸ごと巻き戻る。

適用済みの SQL を後から編集すると次回の実行で止まる。DB には既に流れたものが残っており、
ファイルと実際の状態が食い違うため。**変更は新しい番号のファイルとして追加する。**

`0002_rls.sql` が組織単位の分離（7章）を、`0006_auth.sql` が新規登録の経路
（学校法人を作る → 自分を管理者にする → 学校を登録する）を実装している。
走査・判定の書き込みは service_role キーを持つサーバ側バッチのみ。

**サービスキーは RLS を迂回する。** 走査の経路（`scan/runner.ts`・`/api/cron/scan`）は
学校法人ごとにループし、その組織の設定でその組織の学校だけを走査する。
組織で分けずに全件を取ると、ある組織の設定で別の組織の学校まで走査してしまう。

## 認証と組織（handoff.md 7章）

Supabase Auth のメール＋パスワード。役割は **管理者**（比較校の変更・設定変更・レポート出力）と
**閲覧者**（閲覧のみ）の2つ。組織の分離は RLS に任せ、アプリ側で `org_id` を絞る実装を重ねない。
片方だけ漏れる形にしないため。

| 画面 | 役割 |
|---|---|
| `/signin` | ログインと新規登録 |
| `/auth/callback` | 確認メールのリンクを受け、`code` をセッションに交換する |
| `/onboarding` | 初回のみ。学校法人名と自校を登録し、登録した人が管理者になる |
| `/schools`（08） | 自校の確認と、比較校の追加・削除（5校まで） |

- **未ログインでは分析画面を開けない。** `src/middleware.ts` がセッションを更新し、
  未ログインなら `/signin?next=<元の画面>` へ送る
- **初回登録で入力するのは学校法人名と自校だけ。** 比較校は 08 で追加する。
  最初に5校まとめて入力させると、途中で止まったときに何も残らない
- **比較校として登録した事実は相手校に通知しない。** 登録の関係は `org_schools` に閉じ、
  「誰が登録したか」を相手から辿れる情報は残さない
- **学校の行は組織ごとに持つ（共有しない）。** 同じ学校を2つの学校法人が比較校に
  挙げても別の行になる（`0008_schools_per_org.sql`）。共有すると
  ①他組織が付けた学校名を掴む ②他組織が起こした走査が見える
  ③「前回走査」が他組織の都合で更新され、自分の設定どおりに走らない、が同時に起きる。
  代償として同じサイトを組織ごとに走査するが、クロール範囲も頻度も組織ごとに違うため、
  走査結果はもともと共有できるものではない
- **同じ学校を二重に登録しない。** URL を正規化して突き合わせる
  （`normalizeSchoolUrl`。`www.` の有無・スキーム・末尾スラッシュを吸収する）。
  同じ組織のなかでの重複は DB のトリガでも止める
- **学校を作れるのは、どこかの組織の管理者だけ。** 以前は認証済みなら誰でも
  作れたため、任意の学校名で URL を先に登録できた
- **登録は1トランザクションで行う。** 学校法人・管理者・自校の作成、および
  学校の作成と紐付けは DB の関数にまとめてある（`0009_atomic_registration.sql`）。
  分けて書き込むと、途中で失敗したときにどこからも見えない行や、
  自校の無い学校法人（初回登録に戻れない行き止まり）が残る
- **ログイン後の戻り先は自サイト内のパスだけを受ける**（`safeNextPath`）。
  クエリと確認メールのリンクから入ってくる値なので、外部サイトへ飛ばせないようにする

> Supabase の **Redirect URLs に `<アプリ>/auth/callback` を登録すること。**
> 登録されていないと確認メールのリンクがアプリに戻らず、新規登録を完了できない。

Supabase を設定していないときは認証を使わない。`/signin` はフォームを出さず、
サンプルデータで動いている旨を説明する。押せるのに何も起きない入力欄を作らないため（10章-5）。

## 5つの絶対制約をどこで守っているか

| 制約 | 実装箇所 |
|---|---|
| 計測と解釈を分離する | `analysis/summary.ts` と `analysis/discovery.ts`（02・04）は機械判定のみで、LLM を呼ばない。解釈を生成するのは `persona/`（05）と `actions/inquiry.ts`（06）だけで、どちらも根拠に紐付ける |
| 語句一致で判定しない | `judge/candidates.ts` は候補の絞り込みだけを行い、水準は決めない。`aliases` は候補抽出のヒントとして渡し、プロンプトにも「一致条件ではない」と明記している |
| 比較校を採点しない | `judge/prompt.ts` の `COMPETITOR_SYSTEM_PROMPT` が評価語・比較・改善提案を禁じる。02 の根拠パネルも比較校では記録文のみを出す。06 の照会で LLM に渡す比較校の情報は「何校中何校が公開しているか」だけ（`inquiryBasis`、テストで固定） |
| 走査失敗と欠落を区別する | 判定不能はすべて `unknown`（`judge/judge.ts`）。集計では `unknown` と `n/a` を欠落から除外する（`analysis/summary.ts`、テストで固定）。失敗した走査は保存せず `scan_runs` に記録する（`scan/runner.ts`） |
| 所要時間・期限を生成しない | `types.ts` の `Action` に期限・工数のフィールドを持たない。DB の `actions` にも列がない。06 の照会もプロンプトで見積もりを禁じ、回答欄の脚注に示していないことを明記する |

## 01 SM-02 比較校の更新記録

比較校ごとに直近2回の走査を突き合わせ、**事実だけ**を並べる。出せるのは
「公開しているかどうか」「いつ確認したか」の2つで、評価文・優劣の断定は生成しない。

差分を出さない場面を先に決めてある。ここを緩めると、走査の都合が
「相手校が変えた」という事実の主張に化ける：

| 場面 | 扱い |
|---|---|
| どちらかの走査が完了していない（robots.txt 拒否・失敗） | 何も出さない |
| 判定が `unknown` だった項目 | その項目は比較しない。「分からなかった」を「無くなった」にしない |
| 該当なし（`n/a`）の項目 | 比較しない |
| ページ数上限に当たった走査 | ページの増減を出さない。上限で切られただけのページを変化として書かない |
| ページが無くなった | 記録しない。走査の都合と区別できない |
| 掲載量が thin → full に増えた | 記録しない。公開の有無は変わっていないため |

走査記録が無い／1回目／2回目以降は画面上でも文言を分ける。
「まだ比べられない」ことと「変化がなかった」ことを混ぜないため。

## 07 レポート出力

出力は2通り。どちらも末尾の注記（比較校を評価するものではない旨・校外配布を控える旨）を必ず付ける。

| 出力 | 中身 |
|---|---|
| PDFで印刷する | ブラウザの印刷から「PDFに保存」。用紙の向き・余白・段組は print CSS の `@page` で指定済み |
| HTMLファイルで保存 | 単体で開ける HTML を書き出す。外部の CSS・フォント・画像を参照しないので、開く環境によらず同じ見た目になる |

PDF をサーバ側で生成していないのは、ヘッドレスブラウザを持ち込まない判断（要確定事項 C）に
合わせたため。ブラウザの印刷なら日本語のフォントもそのまま使える。

体裁は2つ。名前付き `@page` で用紙ごと切り替える。

| 体裁 | 用紙 | 中身 |
|---|---|---|
| A4縦（全件） | A4 縦・余白 14mm | 該当する項目をすべて載せる |
| A4横1枚に収める | A4 横・余白 9mm・2段組 | 表を各6行までに絞る |

1枚に収めるときは行を絞るが、**省いた件数を必ず書く**（「他 N 件」）。黙って削ると、
レポートを見た人が「該当がその件数しかない」と誤解する。

## 09 設定画面

走査条件をコードに固定せず、設定画面から変更できるようにしている。値は
`organization_settings`（組織ごとに1行）に保存し、画面・API・走査スクリプトが
同じ入口（`src/lib/data/settings-repository.ts`）を通して読む。変更できるのは管理者のみ。

| 区分 | 設定できること | 既定値 |
|---|---|---|
| 走査スケジュール | 自校・比較校それぞれの頻度（週次／隔週／月次／手動のみ）、実行曜日・実行日・実行時刻 | 自校 週次／比較校 月次、月曜 6時 |
| 判定コスト | 思考深度、1ページあたりの本文上限、1項目あたりの候補ページ数 | low / 2,500字 / 5ページ |
| クロール範囲 | 深度、自校・比較校のページ数上限、リクエスト間隔、同時接続数 | 4／200・60ページ／1,000ms／2接続 |
| 自動実行と通知 | 失敗時に通知するか、通知先の Webhook URL | 通知する／通知先は未設定 |

設定画面では、選んだ頻度での**月あたりの判定数**をその場に表示する（31項目 × 校数 × 走査回数）。
頻度を上げたときのコスト増が、保存する前に見えるようにしている。

次回走査日時の算出（`nextScanAt`）と走査対象の判定（`isScanDue`）は副作用のない純関数で、
日本時間で解釈する。どの学校をいつ走査するかの判断はこの関数だけが持つ。

入力範囲は `SETTINGS_RANGES` を唯一の定義元とし、画面の input とサーバ側の検証
（`validateSettings`）が同じ値を参照する。片方だけ緩い、という状態を作らないため。

## 自動実行

定期実行は `.github/workflows/scan.yml`（GitHub Actions）が週1回、月曜 6:00（日本時間）に
`npm run scan:due -- --run` を回す。外部から叩く口として `/api/cron/scan` も用意してあり、
CLI・cron・Actions のいずれも同じ `src/lib/scan/runner.ts` を通る。
判断も実行も1箇所に置き、経路によって挙動が違う状態を作らない。

Vercel の関数で走査を回していないのは、31項目 × 校数のLLM判定と1秒間隔のクロールを
1リクエストで終わらせるには数十分かかり、関数の実行時間上限（Pro でも 800 秒）を
超えるため。GitHub Actions なら1ジョブ数時間使える。

```bash
CRON_SECRET=$(openssl rand -hex 32)   # .env とデプロイ先の環境変数に設定する
curl -X POST -H "authorization: Bearer $CRON_SECRET" https://<host>/api/cron/scan
```

`CRON_SECRET` が未設定なら自動実行は無効（503）。走査は外部サイトへのリクエストを伴うため、
誰でも叩ける口を開けない。設定画面（09）の ST-04 に、有効かどうかと直近の実行結果を出している。

走査まわりで守っていること:

- **1校の失敗で残りを止めない。** 失敗は記録して次の学校に進む
- **失敗した走査の結果は保存しない。** 空の結果を保存すると、次の集計で「情報がない」になる
- **前回走査とみなすのは走り切ったものだけ。** 失敗を前回扱いにすると次回まで再試行されない
- **学校をまたいで並列にしない。** 学校ごとの同時接続数は設定で絞っているが、
  並列に走らせると実行環境から見た総接続数がその値を超える

失敗があったとき（または走査はできたが判定が付かなかった項目があるとき）だけ通知する。
毎回送ると読まれなくなり、本当に見てほしいときに気づかれない。通知先はメール配信ベンダーを
勝手に選ばず、任意の Webhook URL（https のみ）を設定画面から指定する形にした。
通知に載せるのは学校名・結末・理由だけで、ページ本文は送らない。
通知先が未設定でも、実行の記録（`scan_runs`）は必ず残る。

## 要確定事項（9章）に対して置いた既定値

コードを書き進めるために、handoff.md の推奨に沿って以下を既定にした。**発注者との合意後に変更しうる。**

- **A 判定コスト** — 自校と比較校の頻度差は**設定画面で変更できる**ようにし、既定を「自校 週次／比較校 月次」にした（比較4校で月248判定）。候補ページ抽出で LLM に渡す本文量と思考深度も設定項目にしてある。共通のシステムプロンプトはプロンプトキャッシュ対象。さらに絞る場合は Message Batches API（50%割引）に載せ替えられるよう、1判定=1リクエストの形にしてある
- **B 比較校の走査範囲** — 推奨どおり、比較校は判定に必要なページのみ（既定60ページ、自校は200ページ）。全体集計値は自校のみ
- **C Playwright の要否** — Cheerio のみで実装。JS レンダリングが必要なページのフォールバックは未実装（`crawl/crawler.ts` に差し込み口を残している）
- **D 順位計測** — 検索順位APIの選定は未決のため、ベンダーを勝手に決めずに**手動記録の受け皿**として実装した（`rankings`）。04 の技術チェックと名称ズレの検出は外部API不要のため実装済み
- **E 判定の再現性** — 推奨どおり、前回の判定結果をプロンプトに渡し、変更する場合は `change_reason` に理由を書かせる

## プロトタイプとの差分

- **04 の検索順位** — 上記Dのとおり手動記録。技術チェック（構造化データ・ページタイトル・PDFのみの案内など）と名称ズレの検出は実データから算出している
- **07 の PDF 生成** — サーバ側にヘッドレスブラウザを置かない判断（要確定事項 C）に合わせ、PDF はブラウザの印刷から作る。用紙・余白・段組は print CSS で指定済み。保存できる実ファイルとしては、単体で開ける HTML を書き出す

## 04 発見のされ方

外部APIを使わずに判定できるものだけを機械判定する。走査したページが1件もないときは
「未設定」と断定せず、空の結果を返す（走査失敗と情報がないことを混ぜないため）。

判定するのは、説明会情報の構造化データ、ページタイトルの具体性、説明会情報がPDFのみになっていないか、
説明会ページのURL、画像の代替テキスト、学校の基本情報の構造化データ、見出し構造の7項目。
名称ズレ（SE-03）は、一般に検索される語（`criteria.ts` の `aliases` 先頭）と校内呼称の食い違いを拾う。

## 05 ペルソナ仮説

02・03・04 の判定結果の要約を渡し、学年3種 × 性別2種の6パターンについて仮説を生成する。
仮説には根拠の調査項目IDを必ず持たせ、**根拠のない読み取りは捨てる**（`toPersona`）。
DB 側でも `personas` に、根拠が空の仮説を弾く CHECK 制約を置いている。
欠落だけを並べないよう、支持（support）・欠落（gap）・要確認（check）の3種で持つ。

## 06 照会欄

改善アクションごとに、校内の事情を入力すると位置づけを再評価した回答が返る。
やり取りは `action_threads` に時系列で保存し、次の照会にはそれまでの履歴を渡す。

LLM に渡すのは、その施策の優先度・難易度（定義文つき）、上位に置いた根拠、そして
関連する調査項目について「比較校4校中2校が公開」という件数だけ。比較校の本文や校名は渡さない。
回答は所要時間・期限を出さず、位置づけが変わる場合のみ「優先度の見直し 高 → 中」を添え、
校内でしか判断できないことは「校内で確認すべき点」として返す。

回答が得られなかったときは質問も保存しない。「回答できなかった」ことと
「事情を伝えていない」ことが履歴上で混ざらないようにするため。
`ANTHROPIC_API_KEY` 未設定時は入力欄を無効化し、その理由を画面に出す（10章-5）。

## 10章のQA記録への対応

| プロトタイプで起きたこと | 実装側の対策 |
|---|---|
| 参照先を消した後、参照元が残った | コンポーネント単位に状態を閉じた。共有する対応済み状態は `useActionStatus` 1箇所に集約 |
| 分類ラベルの変更漏れ | `types.ts` の Union 型と Postgres の enum で定義。06 のフィルタ選択肢は `ACTION_SOURCES` から生成し、データに存在する出典のみ表示する |
| 画面名称の取り残し | `screens.ts` に一元化。サイドバー・ボタン・レポート見出し・アクション出典ラベルはすべてここを参照 |
| クラスは書いたがスタイルがない | `prototype.html` の CSS をそのままデザインシステムとして移植。コンポーネント固有のスタイルを足す場合は CSS Modules を併置する |
| 見た目だけでロジック未接続 | 対応済みトグルは `useActionStatus` → `PATCH /api/actions/[id]` に接続済み。01 と 06 で状態が共有されることを確認している。06 の照会欄・05 の生成ボタン・04 の順位記録・08 の比較校追加も同様に接続済みで、権限や鍵が無い場合は押せなくしたうえで理由を出す |
