# School Insight AI — 実装キックオフ資料

このフォルダには、私立中高一貫校向けホームページ分析ツールの実装に必要な資料一式が入っている。

## 読む順番

1. この README で全体像と絶対制約を把握する
2. `prototype.html` をブラウザで開き、01〜07の全画面を実際に操作する。特に **02 欠落マップ**（セルをクリックして根拠パネルを見る）と **06 改善アクション**（グループ化切り替え・照会欄）は操作しないと構造が分からない
3. `handoff.md` を通読する。データモデル（3章）と判定ルール（4章）が実装の核
4. `handoff.md` 10章（QA記録）に目を通す。プロトタイプで実際に起きたバグと、実装で再発させないための設計上の含意をまとめてある

## この製品が何であるか

私立中高一貫校の入試広報担当者が、自校サイトと比較校サイトを客観的に比べ、何をすべきかを事実ベースで把握するための分析ツール。**学校を採点するツールではない。**「情報が公開されているか」という事実の記録に徹し、優劣の評価や煽り文句は生成しない。

3つの計測画面が、それぞれ別の問いに答える：

- **02 欠落マップ** — すでにサイトに来た人が、探した情報を見つけられるか
- **03 導線の実測** — 来た人が説明会の申込にたどり着けるか
- **04 発見のされ方** — そもそも、まだ学校名を知らない人に届いているか

05（ペルソナ仮説）と06（改善アクション）はこの3つを解釈する層。01（サマリー）と07（レポート出力）は提示する層。

## 絶対に外してはいけない5つの制約

実装のどこかで判断に迷ったとき、この5つに立ち返ること。

1. **計測と解釈を分離する。** 02・03・04で表示される数値・事実は機械判定のみで、LLMの解釈を混ぜない。LLMの解釈が入るのは05・06だけで、そこには必ず根拠（criterion_idやURL）を紐付ける。
2. **語句一致で判定しない。** 「探究学習」は学校によって「自調自考論文」「BEYOND」等、名称が全く異なる。ページ内容から意味で判定するパイプラインが必須（詳細は `handoff.md` 4章）。
3. **比較校を採点しない。** 公開の有無・更新日・件数という事実のみを記録する。評価文・優劣の断定は比較校に対して生成しない。
4. **走査失敗と「情報がない」を区別する。** robots.txt拒否・タイムアウト等で取得できなかった場合は `unknown`。これを `none`(欠落)と同じ扱いにすると、取得失敗が「他校にあってお宅にない」という誤った指摘に化ける。
5. **所要時間・期限を生成しない。** 改善アクションに時間見積もりや期限を付けない。学校ごとに体制が違いすぎ、こちらが決めてよい数字ではない。優先度と難易度（「校内でどこまで話を通す必要があるか」）で示す。

## Phase 1 スコープ（`handoff.md` 8章に詳細）

まず作るのは 02 欠落マップ／03 導線の実測／06 改善アクション／07 レポート出力／01 サマリー。
04（発見のされ方）と05（ペルソナ仮説）は Phase 2。理由は `handoff.md` 8章・9章Dを参照（順位計測APIの課金設計が前提のため）。

## 実装前に人間の判断が必要な事項（`handoff.md` 9章）

以下はコードを書き始める前に、発注者側と合意しておくべき事項。仕様として決め切れていない。

- 比較校を全ページ走査するか、判定に必要なページのみに絞るか
- LLM判定のコスト（週次800判定規模）をどう抑えるか、自校と比較校で頻度を変えるか
- LLM判定の揺れ（同じ入力でも結果が変わりうる）をどう扱うか

## デザインの引き継ぎ

`prototype.html` の配色・余白・罫線の太さ・数値の等幅表記をそのままデザインシステムの基準にする。見出しは Shippori Mincho、本文は Zen Kaku Gothic New、数値は IBM Plex Mono。淡色ベースで、分析ツールらしい密度を保つ（詳細は `handoff.md` 末尾）。
